# Admin Application Instructions

Do not hide primary page content or workflows in accordion-style disclosures. Use explicit menus/tabs or always-visible sections instead. The schema workspace has My draft, Published versions, Version comparison and Draft files/server storage tabs. Keep their controllers mounted across tab changes so drafts, validation, comparisons and unresolved saves survive navigation. Schema previews, property fields and compared definitions remain visible within their selected tool.

Prefer a single compact header shared by Overview, Events, Goals and Settings: page title, project selector and report controls on one desktop row, wrapping only when space requires it. Keep connection controls in an anchored disclosure that does not move the header. Remove generic page introductions, promotional taglines and repeated implementation notes; retain actionable errors, empty states, data limitations and field constraints. Maintain readable text sizes rather than shrinking controls to fit.

Header connection/search menus must dismiss on Escape, outside pointer interaction and focus moving outside. Escape returns focus to the trigger; outside interactions retain the newly chosen focus. Preserve inputs on dismissal, allow only one header menu open, respect IME composition, and remove document listeners when the menu owner unmounts.

Account password changes must be directly reachable from the signed-in administrator UI through a separate account screen; keep the change form out of the login screen. The password minimum is 12 characters, with the same rule enforced server-side.

The signed-out administrator entry is a focused, branded login card with the language selector available. Hide analysis navigation and date controls until connected. Keep direct bearer-token connection in a collapsed advanced section, with bounded fields. When no login provider is configured, make the sample demo the available primary action instead of showing a nonfunctional login button. Preserve compact inline reauthentication in connected workspaces.

Keep login body text, notices, form labels, inputs, buttons and language selection at least 1rem on desktop and mobile. Titles are already large enough; do not compensate for small supporting text by enlarging headings. Use readable supporting-text contrast.

Use Inter as the primary admin face for English, Spanish, French, Vietnamese, Indonesian and Malay, with Noto Sans as the fallback. Russian prioritizes Noto Sans. Korean prioritizes Noto Sans KR; Chinese, Japanese, Hindi and Thai prioritize Noto Sans SC, JP, Devanagari and Thai respectively. UI controls inherit the locale font; code and raw identifiers may retain monospace. Use tabular numerals for statistics, table data and chart ticks/tooltips while preserving existing text sizes and monospace identifiers.

Connected Overview, Events, Goals and Settings use the shared text-size tokens: 1rem for body copy, field labels and controls, and at least 0.875rem for metadata, helper text and chart ticks. Keep existing large headings and metric values. Use the 2.75rem control-height token for compact actions; wrap long translations and filters instead of shrinking their text or overlapping neighboring controls. Apply the same sizes in mobile layouts and detailed Settings panels.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build:sites` and `npm run test:sites`; the Sites build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`. Use `npm run build` for the portable app build without Sites metadata.

The selected event-analysis direction is an event explorer with a selected-event detail panel. Enabling previous-period comparison uses a broad event comparison table. Preserve event labels beside their keys, separate browser/server sources, and keep advanced connection settings available without dominating the analysis view.

The selected Goals direction is a goal explorer beside one inspector. Default to the workflow overview with completion rate, outcome counts and daily trend; use separate failure-reason, duration and property-analysis views. Selecting a funnel shows its ordered stage journey, and period comparison uses a current/previous/difference table. Preserve labels alongside registered keys, distinguish pending attempts from confirmed failures, and never describe funnel non-reach as confirmed failure. Keep project/schema/range changes and exports isolated, including when a selected property view unmounts.

The selected Settings direction is option 1: horizontal project/collection diagnostics/schema/SDK/access tabs, with option 4's schema editor beside publication checks. Keep project fields in flat labeled sections and save actions visible. Tab switches must retain drafts, unresolved writes, permission locks and cross-section coordination. Keep JSON and structured forms available; privacy review remains a manual prerequisite after definition validation. Preserve the real numeric limits and paused-project behavior rather than copying illustrative values from generated mocks. Settings has no report date filter; advanced connection/account controls remain reachable without obscuring its tabs.

The selected Overview direction is option 1: an unboxed KPI strip, representative-workflow daily-start bars beside ranked registered events, then an outcome strip. Option 3's service comparison table belongs in a collapsed section below project analytics, read only when opened. Keep service-local recent-seven-day windows distinct from the selected report range and UTC rejection windows. Preserve missing counts/rates and undefined failure events, distinguish pending from confirmed failures, and never infer service health from reception timestamps. Share the compact header and retain source, comparison, export, account and connection controls.

Saylo covers the ZDP twelve-language set (en, zh, es, fr, hi, ko, ja, vi, ru, id, ms, th) across the shell, Overview, event analysis, Goals and detailed Settings (including schema, diagnostics, SDK, access and account controls). Keep one stable client instance/Provider; never key or remount the workspace by locale. Locale preferences may persist separately from auth, but tokens remain in memory. Translate UI copy, not configured project/event/workflow labels, purposes, enums, API codes, JSON drafts, CSV content or generated SDK code. UI locale must not change project timezones or report dates. Keep controller state independent of translated text; display stored helper errors through explicitly registered message templates. Locale changes must not invalidate reads or repeat writes. Load detailed catalogs with the lazy workspace, keeping shell-only namespaces small and every active locale complete. Generate message types with `i18n:types` or typecheck; do not enable Vite-owned typegen output locks in shared local previews.
