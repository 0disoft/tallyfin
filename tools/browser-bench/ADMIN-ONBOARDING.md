# First Project Connection Verification

`verify:admin-onboarding` runs the real administrator UI and browser SDK in an isolated local
environment. It verifies the path from an empty project list through project creation → definition
validation, review, and v1 publication → execution of the generated SDK → retrieval of the first
event. It is not included in the default checks or CI.

## Execution

This requires Node 24 or later and the Playwright setup described in the
[sign-in verification guide](ADMIN-LOGIN.md). It does not install a browser automatically during a
run.

```powershell
npm run build:browser
npm run verify:admin-onboarding -- --channel chromium
```

`--channel` accepts `chromium`, `chrome`, or `msedge`. `--help` prints usage without running.

To include recovery after lost responses, run:

```powershell
npm run verify:admin-onboarding -- --channel chromium --lost-responses
```

This mode commits project creation and schema publication to the local D1 database, then cuts each
successful response 1 time. On the creation screen, click the identical-request confirmation
directly; on the publication screen, click the server-state check directly. Verify that the draft is
preserved and recovered to the next version number and SDK connection without another publication.
The default mode does not cut responses. Distinguish both modes from a real production incident or
remote-provider verification.

## Verification Scope

- Sign in with a synthetic signed provider, then create a project through the UI from an empty
  project list.
- Define the `action_complete` event, then validate it, run the privacy review, and publish the
  first version.
- Compile the code generated by the UI with the currently built `@tallyfin/browser` and send it from
  a real browser. Verify that the browser aggregate in the database and the administrator event table
  each contain exactly 1 row.
- After schema publication, verify that the header updates to `3 SDK connection`. This step alone is
  not proof of event receipt.
- Verify the administrator request's bearer, the absence of credentials in the browser batch, empty
  cookies and local/session storage, and the absence of page errors.

## Isolation and Output

Each run creates a new Miniflare D1 database and Vite cache. Only the onboarding profile grants
project-creation permission to the synthetic account and allows loopback HTTP. The GET-only profile
used by default sign-in verification remains in place. Requests to external origins are blocked
except for synthetic provider responses, and production settings and databases are not changed.

On success, stdout and `.tmp/admin-onboarding-*/report.json` record whether verification passed and
fixed counts. On failure, the tool prints a fixed stage and the code `admin_onboarding_failed` and
exits with code 1. Failure reports and synthetic screen images remain only in the local temporary
folder. Reports do not contain tokens, account identifiers, or source URLs. Temporary material is
excluded from Git and is not deleted automatically.

After 90 seconds, the tool closes the browser and stops the work; final cleanup closes the browser,
Vite, and Miniflare. Total execution time can be longer because of environment setup and cleanup.

A real OIDC provider, production domain, remote database, deployment, and production-service
integration are outside this verification scope. Follow [VALIDATION.md](../../VALIDATION.md) for
execution results.
