# 로컬 수집 클러스터 부하 실험

`npm run bench:cluster`로 실행한다. `--help` 외 인자를 받지 않고 CI·기본 test/check에는
이 2분 실험을 넣지 않는다. URL·자격 증명·원격 대상·기존 DB 경로를 받지 않는다. 각 실행은
무시된 `.tmp/cluster-bench/run-*` 아래 새 D1과 루프백 리스너를 만들고, 성공·실패와 관계없이
finally에서 런타임을 dispose한다. D1과 보고서는 검사할 수 있도록 남긴다.

한 Miniflare/workerd 안에 수집 Worker 3개와 루프백 라우터 하나를 띄운다. 라우터는
`/worker/0/...`부터 `/worker/2/...`까지 해당 수집 Worker로 넘기고 나머지 경로는 404로 거절한다. 세
Worker는 같은 새 D1 ID 하나를 바인딩하고, 응답 헤더 `X-Tallyfin-Bench-Worker`로 실제 실행
인스턴스를 구분한다. JWKS와 임시 서명키·토큰은 메모리에만 있고 외부 인증 제공자에 연결하지
않는다. Worker는 실제 시계를 쓴다. 서울 자정 3분 전에는 보존 기준 날짜 변경을 피하려고
시작을 거부한다. HTTP 요청은 15초 제한이고, CLI는 180초에 취소를 요청한다. 취소·실패 때
새 작업 발행을 멈추고 시작한 작업을 모두 기다린 뒤 런타임을 닫는다.

## 데이터와 부하

6개 합성 프로젝트(load-00~load-05)에 직접 SQL로 영수증·작업 상태·일별 집계를 넣는다. 이
구간은 HTTP 측정에서 제외하며 과거 수집 처리량을 입증하지 않는다. 초기 여섯 테이블 합계는
148,260행이다.

| 테이블 | 초기 행 |
| --- | ---: |
| event_receipts | 67,200 |
| workflow_attempts | 67,200 |
| event_daily_counts | 11,880 |
| workflow_daily_counts | 1,980 |
| funnel_runs | 0 |
| funnel_daily_counts | 0 |

프로젝트마다 영수증 10,000행과 만료 1,200행, 작업 시도 10,000행과 만료 1,200행을 넣는다.
이벤트 집계는 도구 3종 × 등록 이벤트 6종에 90일치와 그 앞선 20일치를 더해 프로젝트당
1,980행이고, 작업 집계는 도구 3종 × 110일치로 330행이다. 퍼널 두 표는 부하 중 퍼널
프로젝트에서만 채워진다.

정리가 끝나면 load 프로젝트는 만료 영수증 7,200행과 만료 작업 시도 7,200행, 90일 이전
집계(event_daily_counts 2,160행·workflow_daily_counts 360행)를 잃는다. 수락된 workflow
배치는 프로젝트마다 영수증 200행과 작업 시도 100행을 더한다.

혼합 퍼널 프로젝트(cluster-funnel)는 따로 등록하고 분당 요청 한도를 600으로 둔다. 브라우저
배치는 `file_selected`/`upload_finished`, 서버 배치는 `job_started`/`job_finished`를
같은 실행 ID 10개에 기록한다. 브라우저/서버 단계는 같은 실행에 합쳐지며 HTTP 도착 순서는
보장하지 않는다. 기대 퍼널 실행 행은 600개이고, 네 단계 도달 수는 각각 600이다.

120초 동안 2초 간격으로 60개 웨이브를 발행한다. 웨이브마다 20개 이벤트 workflow 배치(작업
시도 10개)와 20개 이벤트 브라우저 퍼널 배치, 20개 이벤트 서버 퍼널 배치를 수집 Worker 3개에
같은 본문으로 보낸다. 인증된 요약 3건과 퍼널 일별 3건도 함께 읽는다. 쓰기 540건과 읽기
360건을 합쳐 HTTP 900건, 초당 7.5건이다. 같은 본문을 세 Worker에 동시에 보내므로 한 곳만
수락하고 나머지는 중복으로 응답한다. 기대값은 accepted 3,600·duplicates 7,200이고, 새
workflow 시도 행 600개와 퍼널 실행 600개가 남는다. workflow 배치는 load 프로젝트 6개에
흩어지고 퍼널 배치는 퍼널 프로젝트로만 간다. load 프로젝트의 기존 오늘 집계는 count를
늘리고, 퍼널 프로젝트에는 출처별 이벤트 집계 8행과 단계 집계 8행을 새로 만든다.

실제 scheduled 정리는 1분 간격이 아니라 5초마다 24회 호출하고 Worker 3개에 돌아가며
배정한다. HTTP 작업과 정리가 겹쳐 실행돼야 하며, 만료 영수증·작업 시도와 90일 이전 집계
행이 모두 사라지고 커서 revision이 24여야 한다.

## 검증

수집 Worker 3개가 같은 D1을 읽는지 인스턴스별로 확인하고, 프로젝트별 영수증·작업 시도 수를
초기값+수락분과, 집계의 모든 행을 초기값+수락된 변경분과 대조한다. 퍼널 단계별 도달 수가
600인지, 각 Worker의 퍼널 요약이 startedRuns 600·completedRuns 600·완료율 100인지도
확인한다. 예상 밖 상태·영수증·집계·정리 결과는 실패다.

실시간 절대 일정으로 요청을 발행하고 시작 지연을 따로 기록한다. 동시 작업 한도는 정리를
포함해 16개이고, 한도를 넘길 요청은 속도를 줄이는 대신 명시적으로 실패한다. 실제 HTTP 동시
실행 최대치는 보고서의 `peakHttpInFlight`에, 정리가 HTTP 작업과 겹친 횟수는
`cleanupOverlappedHttp`에 남긴다. 주어진 속도에서 성공했다고 최대 처리 용량을 구했다고
해석하지 않는다.

## 보고서와 한계

`report.json`은 환경·초기/최종 행 수·부하 창/실제 시간·수락/중복·정리 횟수·종류별
p50/p95/max·발행 지연과 요청별 관측을 남긴다. `maxInFlight`는 설정한 상한이고
`peakHttpInFlight`는 실제 최대치다. 이벤트 본문·토큰·키·신원은 남기지 않는다. 실패하면
마지막 단계와 완료 관측을 `failure.json`에 남긴다. 실제 실행 결과와 통과 여부는
[검증 기록](../../VALIDATION.md)에 적는다.

환경 구성은 [Cloudflare Miniflare의 다중 Worker 안내](https://developers.cloudflare.com/workers/testing/miniflare/core/multiple-workers/)와
설치된 Miniflare의 binding API를 따른다.

단일 로컬 에뮬레이터 안의 분리된 수집 Worker 3개를 2분 관찰한 실험이다. 다중 프로세스·다중
지역·장기간 부하·원격 한도/비용·장애 복구·실제 로그인은 미검증이며, 관측 지연에는
호스트·에뮬레이터·암호·DB 작업이 함께 들어가 운영 D1 처리량이나 SLO로 일반화하지 않는다.
정상 부하에서의 성공과 과부하/장애 대응은 별도 검증이다.
