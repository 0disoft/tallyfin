첨부한 Tallyfin 소스 압축파일을 직접 읽고, 실제 사용과 운영에 도움이 되는 개선을 수행해 주세요.
일반적인 체크리스트나 전면 재작성 제안보다, 현재 코드에서 근거를 찾은 결함과 병목을 우선해 주세요.
이미 해결된 문제를 다시 제안하지 말고 최근 개선 코드 자체의 결함이나 부작용도 검토해 주세요.

1. 프로젝트와 첨부파일

Tallyfin은 개인정보 수집을 최소화하는 제품 이벤트 분석 시스템입니다.
TypeScript 모노레포이며 core, storage-d1, browser/server SDK, OIDC 인증,
Cloudflare Workers 수집기, React/Vite 관리자 앱으로 구성됩니다.
결제, 광고 어트리뷰션, 세션 리플레이, 방문자 식별 시스템은 제품 범위 밖입니다.

압축파일은 Git에서 추적하는 현재 소스를 담은 스냅샷입니다.
Git 이력, node_modules, 빌드 산출물, 캐시, 로컬 DB, 운영 자격증명은 포함하지 않습니다.
공개 설정 예시, 테스트 fixture, 마이그레이션, 패키지 잠금 파일과 원본 이미지 자산은 포함합니다.
정확한 스냅샷 커밋과 파일별 SHA-256은 압축 안의 SOURCE-SNAPSHOT.json을 확인하세요.
Git 메타데이터가 없다는 이유로 소스를 미완성으로 판단하거나 새 Git 저장소를 만들지 마세요.

2. 먼저 읽을 기준 문서

- AGENTS.md: 저장소 범위와 변경 규칙. 실제 작업에서는 가장 가까운 지침도 확인하세요.
- docs/product/02-spec.md: 제품 범위와 정책.
- docs/adr/: 기존 기술과 설계 결정. 새 기술로 대체할 필요가 있는지 먼저 입증하세요.
- api/openapi.yaml: HTTP 입출력과 오류 계약.
- db/schema.dbml 및 db/migrations/README.md: DB 계약과 적용 순서.
- VALIDATION.md: 최근 구현과 검증 기록. 과거 기록을 현재 실행 결과로 표현하지 마세요.
- DEVELOPMENT.md 및 각 package.json: 실행 가능한 실제 명령.

로드맵의 미완료 표시나 문서 설명만으로 미구현이라고 결론 내리지 마세요.
문서와 구현이 다르면 실제 호출 경로와 테스트를 확인해 차이를 설명해 주세요.
소스에 없는 운영 설치 값, 실제 OIDC 제공자 설정이나 배포 상태를 만들어내지 마세요.

3. 최근 반영한 작업: 검토의 출발점이며 정확하다고 가정하지 마세요

- 시간, 난수, 외부 I/O의 선택적 주입과 요청 수명/취소 처리 개선.
- 인증·권한·입력 검증 순서를 보존한 제어 흐름 분리와 정책 상수 정리.
- DB revision/CAS를 통한 수집, 관리자 권한, 발행자 회수·재부여 경합 보호.
- 외부 호출 기한, 비공개 cause 보존, OIDC 장애와 인증 거부 구분.
- 기존 멱등 수집 재전송의 시간/횟수 예산 안에서 양수 jitter 적용.
- 이벤트/workflow 정의와 집계 버킷의 Map/Set 인덱싱.
- 관리자 ApiClient별 GET 동시 4개, FIFO 대기 최대 64개.
  선택적 maxConcurrentReads는 1~16이며 본문 읽기까지 슬롯을 유지합니다.
  취소를 무시하는 I/O는 실제 종료까지 슬롯을 점유하고 쓰기는 대기열을 우회합니다.
- 0011_analytics_lookup.sql의 이벤트/퍼널 조회 인덱스.
  실제 로컬 D1 실행 계획에서 이벤트/퍼널 일별 조회의 임시 정렬 제거를 확인했습니다.
  퍼널 속성 분류의 일자 안 정렬은 남으며 workflow에는 새 인덱스를 넣지 않았습니다.
- 정리 작업의 선택적 clock/signal/maxPages, 20초 이후 신규 작업 시작 중단,
  30초 DB 기한, 처리한 앞부분의 커서 CAS 저장, 한 실행 안 프로젝트 중복 방지.
  기본 한 페이지·5개 프로젝트는 최대 50 SQL을 유지합니다.
  호스트가 예산을 확인해 cleanupMaxPages를 지정할 때만 최대 4페이지·20개·200 SQL입니다.
  개별 프로젝트·테이블당 500행 한도를 유지합니다.

마지막 구현 커밋은 3cc22cc, 69bedc6, 6ae79eb, 77d270c입니다.
Git 이력은 빠져 있으므로 해당 커밋을 조회할 수 있다고 가정하지 마세요.
코드와 VALIDATION.md에서 실제 내용을 확인하세요.
기록된 최종 검증은 루트 테스트 508/508, 관리자 287/287,
번들/Sites 13/13, 관련 TypeScript 검사와 관리자 빌드 통과입니다.
운영 부하, 대규모 인덱스 생성 시간과 저장 비용, 실제 운영 제공자는 검증하지 않았습니다.
이 수치를 새로 실행한 검사나 운영 성능 보장으로 재사용하지 마세요.

4. 우선 검토할 실제 코드와 질문

A. 정확성과 경계값
packages/core/src/, packages/storage-d1/src/와 SDK의 호출 경로를 함께 확인하세요.
시간 창의 직전/정각/직후, 시간대·DST·자정, 과거/미래 시각, 안전 정수 오버플로,
null/누락/false/0의 차이, 중복 ID·순서 뒤집힘·충돌·지연 도착을 검토하세요.
각 의심 사항에 실제 실패 입력과 기대 결과를 제시하세요.

B. 동시성·권한·취소·자원 수명
apps/collector/src/dependency-lifetime.ts, cleanup.ts,
packages/storage-d1/src/maintenance.ts 및 쓰기 경로,
packages/auth-oidc/src/, apps/admin/src/api/read-scheduler.ts,
request-lifecycle.ts, response-body.ts와 인증 코드를 확인하세요.
여러 Worker/요청의 read-modify-write가 DB 수준에서 보호되는지,
권한 회수/재부여와 커밋 사이의 경합을 막는지 확인하세요.
취소·시간 초과·예외·응답 본문 지연·컴포넌트 해제 때 타이머/리스너/슬롯이 남는지,
이전 응답이 새 프로젝트나 세션의 상태를 되살리는지 검토하세요.

C. 장애 격리와 재시도
공유 토큰 갱신, JWKS 조회, D1 batch와 SDK 전송을 함께 확인하세요.
상위 취소 이유와 원본 cause를 보존하면서 공개 응답/로그에는 비밀이 새지 않아야 합니다.
읽기라고 무조건 재시도하지 말고 실패 유형·횟수·총 기한·Retry-After를 검토하세요.
쓰기의 멱등성은 HTTP 메서드가 아니라 요청 식별자와 저장 계약으로 판단하세요.
결과가 불명확한 쓰기에 무조건 재시도를 붙이지 마세요.

D. 데이터 증가와 실제 성능
배치 안 반복 탐색, 불필요한 복사/JSON 파싱, N+1 호출, 과도한 응답·메모리 사용,
쿼리 실행 계획, 전체 스캔, 인덱스 유지 비용과 정리 적체를 확인하세요.
이론적인 O(N) 개선만 제시하지 말고 현재 최대 입력 크기와 호출 횟수로 효과를 판단하세요.
정렬 순서·첫 일치 규칙·타입별 집계·중복 처리 규칙을 보존하세요.
D1의 단일 DB 직렬 처리, 바인딩·SQL·실행 한도를 고려하세요.
공식 플랫폼 한도를 언급한다면 최신 공식 문서로 검증하고 출처를 적어 주세요.
무제한 Promise.all이나 무조건적인 새 인덱스 추가를 해결책으로 삼지 마세요.

E. 구조와 유지보수
40줄을 넘거나 중첩이 깊은 함수, 40KB를 넘는 파일을 후보로 보되,
분리 자체를 목표로 삼지 말고 변경 위험과 테스트 격리가 실제로 개선되는지 판단하세요.
호출자가 준 객체/배열의 변경과 함수 내부 로컬 배열의 push를 구분하세요.
도메인 정책 상수를 묶되 서로 다른 정책을 우연히 같은 숫자라는 이유로 합치지 마세요.

5. 변경 조건

- 필수 함수 입출력 시그니처, 인증 → 권한 → 입력 검증 → 상태 조회 순서,
  HTTP 상태·오류 코드·응답 형태를 기존 계약대로 유지하세요.
- 시간/난수/I/O/signal 주입은 가능한 한 선택적 인자로 추가하세요.
- DB 불변식, 원자적 저장, 멱등 수집, 권한별 데이터 분리를 보존하세요.
- 필요한 스키마 변경은 새 번호의 마이그레이션으로 추가하세요. 기존 SQL을 고쳐
  이미 적용된 DB와 새 설치의 구조를 다르게 만들지 마세요.
- DBML·OpenAPI 등 실제로 영향을 받는 기준 문서와 좁은 회귀 테스트를 함께 갱신하세요.
- SDK의 기존 크기·전송 예산과 호스트 기본 쿼리 예산을 보존하세요.
- 필수 의존성/프레임워크 교체나 전체 재작성은 구체적 필요가 입증되지 않으면 하지 마세요.
- 새 제품 기능보다 현재 기능의 실제 오류와 성능 병목 제거를 우선하세요.
- 원격 업로드, 푸시, 배포, 운영 DB 적용, 자격증명 생성/로그인은 수행하지 마세요.
- 비밀값이 필요해 보이면 가짜 운영 값을 만들지 말고 필요한 설정과 막힌 범위를 적으세요.

6. 수행과 검증

먼저 근거가 있는 문제를 영향·발생 가능성·수정 비용으로 정렬하고 상위 문제부터 처리하세요.
문제없는 항목과 일반론은 생략하세요. 코드에서 확인한 결함, 재현한 결함,
조건부 위험, 추가 정보가 필요한 가설을 구분하세요.
실행 환경이 있다면 가능한 범위에서 직접 수정하고 좁은 재현/회귀 검사를 먼저 실행하세요.
작업이 길어지면 독립적으로 검토할 수 있는 작은 변경 단위로 나누세요.
환경이 없다면 실행한 것처럼 표현하지 말고 최소 재현 코드·unified diff·검증 명령을 제시하세요.
Git이 없는 압축 스냅샷에서는 변경 파일이나 패치를 제공하면 됩니다.

명령은 package.json과 DEVELOPMENT.md를 기준으로 선택하세요. Node >=24가 필요합니다.
루트 테스트의 기존 경로를 유지하면서 로컬 과부하를 줄인 실행 예시는 다음과 같습니다.
node --test --test-concurrency=2 --test-timeout=30000 packages/*/test/*.test.ts apps/*/test/*.test.ts tools/provision/test/*.test.ts tools/runtime/test/*.test.ts
관리자 변경 시 npm run test:admin, npm run typecheck:admin, npm run build:admin을 참고하세요.
이미 통과한 동일 입력의 검사를 불필요하게 반복하거나 기본 CI를 무겁게 만들지 마세요.
새 버그를 막거나 실제 위험을 검증하는 테스트에 집중하세요.

7. 최종 결과 형식

답변은 한국어로 작성하세요.
먼저 가장 중요한 발견과 실제 수정한 내용을 짧게 설명하세요.
그다음 문제별로 다음 내용을 표나 짧은 목록으로 제시하세요.
우선순위 / 파일·함수·라인 / 구체적 실패 시나리오 / 근거와 재현 여부 /
수정 내용 또는 최소 패치 / 필요한 경계값 테스트 / 호환성·성능 비용.

마지막에 변경 파일, 실제 실행한 명령과 결과, 실행하지 못한 검사와 이유,
남은 위험·미결정 사항을 정리하세요. 수정 파일 묶음이나 unified diff도 제공하세요.
실측 없이 개선 배율·운영 준비 완료를 주장하지 마세요.
