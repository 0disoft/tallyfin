4. Actual code and questions to review first

A. Correctness and boundary values
Check packages/core/src/, packages/storage-d1/src/, and the SDK call paths together.
Review just before, exactly at, and just after time windows; timezones, DST, and midnight; past and future times;
safe-integer overflow; differences among null, missing, false, and 0; duplicate IDs; reordered, conflicting, and late-arriving data.
For each suspected issue, provide the actual failing input and the expected result.

B. Concurrency, permissions, cancellation, and resource lifetime
Check apps/collector/src/dependency-lifetime.ts, cleanup.ts,
packages/storage-d1/src/maintenance.ts and the write paths,
packages/auth-oidc/src/, apps/admin/src/api/read-scheduler.ts,
request-lifecycle.ts, response-body.ts, and the authentication code.
Verify whether read-modify-write operations across Workers and requests are protected at the DB level,
and whether races between permission revocation or re-grant and commits are prevented.
Check whether timers, listeners, or slots survive cancellation, timeout, exceptions, delayed response bodies,
or component unmounting, and whether an old response can restore state for a new project or session.

C. Failure isolation and retries
Review shared token refresh, JWKS lookup, D1 batches, and SDK delivery together.
The upper cancellation reason and original cause must be preserved while secrets do not leak into public responses or logs.
Do not retry every read unconditionally; examine failure type, count, total deadline, and Retry-After.
Judge write idempotency from the request identifier and storage contract, not the HTTP method.
Do not attach unconditional retries to a write with an unknown result.

D. Data growth and actual performance
Check repeated scans inside a batch, unnecessary copies or JSON parsing, N+1 calls, excessive response or memory use,
query plans, full scans, index maintenance cost, and cleanup backlog.
Do not present only a theoretical O(n) improvement; judge the effect from the current maximum input size and call count.
Preserve sort order, first-match rules, type-specific aggregation, and duplicate handling rules.
Consider D1's single-DB serial processing and binding, SQL, and execution limits.
When citing official platform limits, verify them against the latest official documentation and cite the source.
Do not treat unbounded Promise.all or unconditional new indexes as solutions.

E. Structure and maintainability
Consider functions longer than 40 lines or deeply nested functions and files over 40KB as candidates,
but do not make splitting the goal; judge whether the change risk and test isolation actually improve.
Distinguish changes to caller-provided objects and arrays from pushes into local arrays inside a function.
Group domain policy constants, but do not merge different policies merely because they happen to share the same number.
