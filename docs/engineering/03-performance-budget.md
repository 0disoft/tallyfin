# 성능 예산

이 문서는 Tallyfin의 성능 목표다. 코어·저장 어댑터·최소 수집기는 로컬에서 검증했다. 수집 SDK·운영 벤치마크는 아직 없다.

## 목표

- 공통 브라우저 SDK와 한 서비스의 연동 코드·필수 설정을 합쳐 증분 목표는 ≤3KiB gzip이다. 호스트 앱 전체나 모든 프로젝트의 설정 합계가 아니다. 프로젝트별 설정도 전송 크기와 초기 실행 비용에 포함한다.
- 동기 수집 I/O를 두지 않으며 렌더링·계산에서 전송 완료를 기다리지 않는다.
- 측정 전에는 달성 수치를 주장하지 않는다.

## 버퍼와 전송

- 크기가 제한된 메모리 버퍼에 이벤트를 모은다.
- 주기적으로 배치를 전송하고, 탭이 숨겨질 때도 남은 배치 전송을 시도한다.
- sendBeacon/keepalive는 전달 보장이 아니다.
- 계약 한도: 40개 메모리 버퍼, 배치당 20개/16KiB, 5초 전송, 최대 2회/10분 재시도, 영수증 48시간. 구현 성능과 비용은 아직 측정하지 않았다.
- 유계 재시도, 배치 멱등성, 원자적 집계, 입력·속도 제한이 필요하다. Worker 메모리 카운터는 영속 집계로 쓰지 않는다.

## 측정 방법

- 기준선(비활성)과 활성 상태를 동일 조건에서 비교한다.
- 상호작용 지연, SDK 실행 시간, 전송 크기를 함께 본다.
- Sembom 외의 다른 서비스에서도 확인한다. 모든 프로젝트의 이벤트 정의를 브라우저에 한꺼번에 내려주지 않는다.
- 프로젝트 수·등록 속성 조합·동시 전송량에 따른 수집/저장 비용은 별도로 측정한다. 서버 연동의 처리 지연 예산은 후속 구현에서 정한다.
- 정확한 지연·전송 예산은 UNDECIDED이며 측정된 주장은 없다.

## 실패 처리

- 수집 실패는 연결된 서비스의 화면이나 업무 처리에 영향을 주지 않는다.
- 프로젝트 paused 상태는 수집을 거부한다. SDK 연결 해제와 배포별 비활성 구현은 후속이다.
