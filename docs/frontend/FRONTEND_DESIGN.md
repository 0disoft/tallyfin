# Tallyfin Frontend Design

## Settings tabs and schema workbench — 2026-10-28

The API Settings page uses the existing compact 220px navigation shell, a project
picker, expandable connection/account controls and five horizontal tabs:
project, collection diagnostics, event schema, SDK connection and access.
Settings has no analytics date selector. Its expanded connection controls stay
in the header layout rather than covering the tab strip.

`LiveSettingsWorkspace` owns only the selected tab and keyboard navigation
(Left/Right/Home/End). Panels remain mounted and hidden so the existing settings,
schema, grant and publisher controllers retain dirty drafts, pending writes,
access coordination and their registered exit checks. `LiveSettings` shares one
controller across its project/access panels; diagnostics includes the existing
storage check and operational report. Server and API state ownership is unchanged.

The project form groups identity/status, allowed origins, admission limits and
read-only timezone into flat labeled rows with a persistent save/reset bar.
Actual limits remain 1–600 requests/minute and 1–1,000,000 new receipts/UTC day;
pausing stops both browser and server ingestion. The allowed-origin list applies
only to browser requests. No policy is inferred from the generated mock values.

`LiveSchemas` presents JSON/structured editing beside validation and manual
privacy review. Structured error targets reveal the relevant editor before
focus moves; malformed JSON reveals the textarea. Version history/comparison,
local draft files and server drafts remain available in expandable utilities.
Publishing still requires the current validated definition and privacy review;
the existing controllers retain conflict/lost-response and permission recovery.
All styles are scoped; panels stack on mobile and tabs scroll within their strip.
No API/DB contracts, URL state, persistent browser state or sample-mode settings
behavior changed.

## Server draft saving — 2026-10-24

`LiveSchemas` connects `ServerSchemaDraft` as an area independent of the file feature. It is a project-owner shared draft, and reading, saving, and loading are all explicit actions. Saving is locked before the first confirmation, and a server query does not change the current input. Controls are locked during reader, validation, publishing, list loading, and permission checks, and the previous server content is hidden. There is no version reservation or automatic publishing.

The query and save state is owned by `SavedDraftController`, while input, validation, and privacy review are owned by the existing SchemaEditor. The controller is created and disposed inside an effect for each session, client, project, and editor lifetime, so a StrictMode rerun does not reuse an instance that was discarded. It subscribes to the editor synchronously, cancels queries and saves on busy transitions, and ignores late results. Cancelling a write does not guarantee that the commit is cancelled, so cancelling during a save also requires checking the result again.

A save uses only the revision last read, and conflicts and lost responses are not retried automatically. After a new query, the server content and current input can be expanded and compared, and the user can choose to load the server content or keep the current input and review the next save. The latter performs no write. When the submitted content and the re-queried content are exactly equal, the save is confirmed, while local input changed after submission remains unsaved.

SchemaEditor separately remembers the [version input, raw JSON] pair confirmed by the server. The leave warning clears only when the current pair equals that value, and unpublished changes remain protected. JSON array keys are used instead of delimiter strings so newlines in an incomplete version cannot collide with the body. Replacement confirmation for file and server loading remains in the separate hasDraftInputChanges state, and server confirmation alone does not clear validation or review. Loading requires new validation and review. Server content is not placed in URLs, browser storage, analytics, or logs.
Save confirmation is reflected synchronously in the editor before the result is displayed, and beforeunload also checks the latest hasUnsavedChanges at event time so an effect-cleanup delay cannot create a false unsaved warning.

Buttons lock according to the asynchronous phase, and status and alert regions announce progress, save results, conflicts, and unsaved input. Server and current raw text use the keyboard scrolling and small-screen vertical layout of the existing schema-comparison view.
`verify:admin-server-draft` checks restore, conflict, loss and late responses, and permissions with synthetic OIDC and local D1.

When event, workflow, or funnel members are the same, a reorder is still shown as a separate row. The representative workflow is included; project settings, publication date, and usage state are not compared.

The UI provides two version selections, explicit compare and retry, and loading, error, identical-definition, and insufficient-version states. In-progress requests are cancelled and previous results hidden on selection changes, list or permission lock, project or client changes, and unmount. When refreshTick changes, old results for the same request are also hidden. Late success or failure does not overwrite the current request. 401 and 403 use the existing ApiClient access-denial propagation. A notice beside the table says compatibility and aggregate comparison are not judged automatically.

Selections use a label, results use status and alert, and the table provides a caption, row and column headers, and keyboard horizontal scrolling. On a small screen, the selections and buttons are stacked vertically and only the table scrolls horizontally.
`verify:admin-schema-comparison` checks pagination, inactive versions, draft and review preservation, reader access, errors and retries, late responses, project changes, and permission revocation with synthetic OIDC, local D1, and actual Chromium.

## Schema draft files — 2026-10-24

`SchemaDraftFiles` was added to the schema editing area of `LiveSchemas`. In the owner's editable ready state, it downloads the current JSON and target version as a `tallyfin.schema-draft/v1` file and reads it back. The file allows only the four fields `format`, `projectId`, `targetVersion`, and `draftText`, and its project ID must match the current project. The whole file is at most 128KiB in UTF-8. The internal draft preserves syntactically incomplete JSON, and the target version preserves any string of 32 characters or fewer, including an empty value or an invalid number.

When the definition or version differs from the editor baseline, it asks for browser confirmation before importing, and cancelling leaves the draft, version, validation results, and privacy review unchanged. A confirmed import clears previous validation results and privacy review and does not validate or publish automatically. File reading happens only inside the browser with `FileReader`; it does not upload to the server, save a draft, reserve a version, or poll automatically. Loading works only in the ready state and in the owner editing scope that is not loading more list pages, and the file button is locked during loading, validating, publishing, review, loading more, reader access, and permission loss. Status and alert regions announce reading progress, success, and errors.

`read-schema-draft-file.ts` handles ArrayBuffer reading and UTF-8 fatal decoding. A UTF-8 BOM is allowed, and invalid bytes produce a fixed error. Input over 128KiB is rejected before FileReader is created. An invalid format, a project mismatch, a read failure, and the 10-second timeout are reported as form errors. Success, failure, user cancellation, and the 10-second timeout all release timers, handlers, and signal listeners and abort an in-progress reader. The original read error is preserved as the cause.

`SchemaDraftFiles` shows the file name being read and a cancel button and moves focus to the error notice. Cancelling replacement or a user read reports that existing input and review state were retained. Because it subscribes to the editor synchronously, an in-progress read is cancelled even if React batches the busy-to-ready transition. Changing the editor, project, or editable state and unmounting are also cancellation boundaries. Replacement confirmation uses the latest input state when reading finishes, and if importDraft rejects because state changed, the result is not shown as success. The input value is cleared immediately so the same file can be selected again after failure or cancellation. File import makes no additional API calls.

## Previous-period comparison of failure causes — 2026-10-23

When the goal screen's existing period-comparison switch is enabled, WorkflowFailureReasonComparison appears. LiveDashboard passes only results matching the current key from the existing usePeriodComparison to LiveGoals and matches the previous result by workflow ID. There are no additional queries, timers, storage, or global state. Disabling comparison removes the table, while project, version, and period changes and permission revocation follow the existing analytics lifetime.

The screen and CSV share compareFailureReasons. Overall failure rate is confirmed failures divided by start attempts, and the numerator and denominator are shown side by side. Cause share uses all confirmed failures in each period as its denominator. It shows current and previous counts, shares, and difference in percentage points (%p) for each cause, missing and unmeasured cause rows, and the measurement state of both periods. It explains that a change in cause share does not mean an increase in overall failures and warns that an in-progress cohort may change. It does not automatically judge an incident or statistical worsening.

Cause share difference is calculated only when neither period has unmeasured failures and a failure denominator exists. When unmeasured data remains, observed counts and shares are kept and the change is held. An entirely unmeasured period or an older response shows a dash instead of 0. No failures and no starts are distinguished, and the computable overall failure rate is retained even when the cause comparison is held. When the previous period is loading, fails, or has a partial workflow failure, the previous comparison table is hidden and the current distribution is retained. It guides the user to retry the existing comparison, and CSV locking follows the existing upstream state handling. Both tables provide names, row and column headers, and keyboard horizontal scrolling.

CSV adds previous_count, previous_share_percent, and failure_reason_comparison_status after the existing columns. Cause comparison rows and overall failure-rate comparison rows use the same calculation and retain the held state and blank change value. The previous period's measurement scope and denominator can be checked in the existing previous rows.

## Discarding response bodies after cancellation — 2026-10-23

The default fetch wrapper preserves the body, and ApiClient remembers the response when transfer completes. It also requests disposal of a response that arrives after cancellation and a body whose JSON read did not start because the timeout occurred exactly when headers were received. A disposal request for the same response is sent only once, and a cancel failure or indefinite wait does not override the caller's cancellation reason or deadline error or delay the return. A read slot is not returned before fetch or json actually finishes. The injected transport body is optional, preserving the existing json-only contract, GET execution and wait limits, and write bypass.

## Native fetch response memory protection — 2026-10-12

`apps/admin/src/api/response-body.ts`'s `readResponseJson` limits the administrator API response body by byte count before parsing, only on the default native fetch path. Success responses allow up to 4MiB (`MAX_ADMIN_RESPONSE_BYTES`) and error responses up to 16KiB (`MAX_ADMIN_ERROR_BYTES`), and a non-numeric or over-limit `Content-Length` is rejected immediately before the body is read. Without a header, reading stops as soon as accumulated bytes exceed the limit. Received bytes are gathered into one buffer that starts at 4KiB and doubles up to the limit, with no separate string accumulated for each chunk. UTF-8 is decoded once at the end with a `fatal` decoder so invalid bytes are treated as a contract error rather than silently changed. When the caller cancels, reading stops with `reader.cancel()`, and cleanup does not delay or replace the result. An injected `fetchImpl` keeps the existing json-only test and transport contract and does not apply this limit directly.

`client.ts` confirms 401 and 403 from status before reading the body, preserving permission locking and analytics access cancellation propagation. If a success body cannot be read as JSON, it ends with a `contract` error, and if parsing an error body fails, the existing HTTP status message is used. The screen shows an explicit `Retry` control and there is no visual change. API, DB, and public SDK contracts are unchanged. Validation results are in VALIDATION.md.

## Synchronous delay enforcement in administrator request limits — 2026-10-12

Because `ApiClient`'s 15-second request limit relied only on a `setTimeout` callback, a `getBearer` callback that blocked the event loop synchronously could delay the timer and allow a write such as PATCH to be sent after the deadline. The request now records its end time from the `performance.now()` monotonic clock at the start and rechecks elapsed time immediately after credential acquisition, immediately before sending, when response headers arrive, and when JSON completes successfully or with an error. If the limit has passed before sending, it does not start the HTTP request; if time passes while reading the response, it does not undo a request already sent and ends with the existing `timeout` error. A caller abort is not overwritten with timeout.

An already observed 401 or 403 remains a permission error even if the error body stalls or passes the deadline, and the analytics access cancellation notification is delivered. Shared login refresh is retained for other requests, and saves are not retried automatically. A save with an unknown result still requires the latest state check and explicit reconfirmation. API and DB contracts and dependencies are unchanged. Validation results are in VALIDATION.md.

The notification occurs as soon as the status is seen even if the error body stalls. The parent clears query results for that connection and project and removes analytics components and CSV input. Closing detail, comparison, or breakdown or moving to another screen retains the denied state, and only an explicit refresh or reconnect checks the server again.

The denial stays only in memory and is bound to the connection, project, and refresh generation. Cancelled requests and late responses from a previous connection or project do not lock the current screen. A 403 on owner-only settings or permission queries or writes is not interpreted as a reader losing analytics permission. Other failures such as 404, 409, and 503 keep the existing screen-specific recovery behavior. API and DB contracts and server permission decisions are unchanged.

## Blocking unsupported timezone responses — 2026-10-12

Timezones in the project list and query metadata are checked at the API boundary. An unsupported name stops before the screen is drawn with a `contract` error, and `LiveDashboard` shows `The response does not match the contract` and `Retry`. Previously this value passed validation and threw during query date calculation, and the `DeferredPanel` error boundary only offered a refresh that cleared entered content and in-memory tokens. Retry repeats the same query while retaining the connection and login.

The validation rules match the Core project registration contract (1 to 64 characters, `^[A-Za-z][A-Za-z0-9_+./-]*$`, and a name the browser can format). Server-provided supported timezones and aliases are displayed as-is without rewriting or converting them to UTC. `DeferredPanel`'s refresh guidance remains for unexpected render errors, and a timezone response does not reach that path.

## CSV query-source column — 2026-10-12

The last CSV column, `query_source`, records the source the user queried (browser or server) on every row. The existing `source` column remains and means the declared event source on `event_total` rows and `meta.source` on other rows. An `event_total` row for an unselected source keeps `availability=not_selected` and a blank `count` and is not filled with 0. Column order is retained and the new column is appended only at the end. CSV readers should look up columns by header name rather than assuming a fixed column count.

## Per-screen analytics queries — 2026-10-23

The events screen reads only the summary, the individual overview reads the summary and the workflow referenced by `representativeWorkflowId`, and goals reads the summary and all workflows. The previous period uses the same scope. Screen scope is retained in an internal snapshot, and CSV validates scope and required workflows. The existing full-snapshot call and result removal on permission loss are retained.

## Per-project schema selection — 2026-10-23

The first query selects the latest active version, and manual input is remembered per connection and project. Project and connection changes do not display responses from the previous scope. When there is no active version, analytics selects the latest past version, and SDK guidance directs the user to publish an active schema. Version-checking and failure states are shown and refresh checks again. Pages are traversed in descending order, with cancellation and propagation of the original error.

## Cleanup throughput observation — 2026-10-23

The operations log report validates optional cleanup.execution and shows the count by stop reason, maximum runtime, maximum scheduled-execution delay, aborted work count, and confirmed cursor progress in the retained-cleanup area. It shows the number of samples with diagnostics and scheduled delay separately and notes that time and page limits were carried into the next run. It distinguishes traversal completion from deletion of all data and cursor progress from deletion success. When an older report has no execution, it does not invent and display times. Existing local file reading, worker lifetime, and input limits are unchanged, and no network access or automatic refresh is added.

Cleanup logs and the report's optional `metrics` include deletedRows, saturatedTables, oldestExpiredReceiptAgeMs, measuredProjects, and capacityLimitedProjects. Duplicate logs are counted once, maximum delay keeps the maximum value, and older unmeasured logs are not converted to 0. Delay represents only expired receipts left in projects that were successfully processed, and reaching the deletion limit is not a confirmed backlog judgment. The previous logs for up to 20 projects continue to be read.

## Returning to automatic version selection — 2026-10-23

Turning off the automatic schema-selection checkbox pins the current version, and entering a version directly also switches to manual mode. Turning the checkbox back on clears only that project's pinned value and checks the latest active version again. Manual selections in other projects are retained, and mode changes are blocked while an automatic version query is in progress.

## Partial goal-query failures and the integration overview — 2026-10-23

When a workflow daily query on goals fails with a general error or contract error, only that panel shows the error while healthy workflows and funnels remain. Retry in the failed panel reads only that one workflow and merges it in definition order. A screen-scope change cancels and late responses are discarded. 401 and 403 continue to propagate to whole-analytics permission handling. When a workflow is missing from the current or previous period, the whole CSV is locked and incomparable values remain null. The previous period can be read again separately.

The integration overview on the overview screen reads at most 5 projects on the current page only when explicitly opened. It reads the project list with one `GET /v1/overview` call and applies the existing API client's HTTP limit. It does not pre-read every project or poll automatically. It shows the latest active schema; recent and previous 7-day events for the selected source; the completion rate and change of the workflow referenced by `representativeWorkflowId`; recent project-wide receipts; and the DB rejection count for the recent 7 UTC days. When the field is absent, completion rate and workflow name are null and are not replaced with the first registered workflow.
Completion rates are not summed across services. No active schema, permission and query failure, and completion or rejection query failure are distinguished from a real 0. Page changes and disconnect cancel in-progress reads. If there are more projects in the list, additional authorized project pages can be read. The server selects the period in the project timezone and the latest active version. A denied row is also passed to the existing detail analytics permission-loss handling, with its numbers blanked. HTTP 401 and 403 propagate to every requested project before the body completes. A validation failure in workflow or rejection data blanks only that panel and retains valid event counts. Rejections are a best-effort total after per-page permission checks, and a partial total from a mid-read failure is not displayed. A shared metadata or analytics DB execution failure marks the whole query as failed.

A row with no active schema still shows recent receipts and rejection totals. Events and completion rate remain not comparable, and the workflow cell explicitly says there is no active schema. When only the rejection query fails, known recent receipts remain and only the rejection cell shows a query failure. A confirmed permission loss blanks the entire row.

The workflow cell in the integration overview shows current and previous success, start, in-progress, and selected failure counts. Change in percentage points is shown only when neither period is still aggregating and there are at least 30 starts. The 30-start threshold governs display only and is not a statistical-significance or incident-warning threshold. Because the current period includes today, comparison is usually held as aggregating. A response from an older server without sample counts shows only ratios and holds change as `sample information unavailable`. A failure panel, no schema, or permission loss does not retain previous numbers.

The integration overview retains the server's generatedAt and displays it as the UTC query-basis time. It shows each service's local current and previous periods and the actual UTC 7-day range of its rejection records. The row period is validated against server time and must match the project's existing timezone. When an older server has no period field, it does not estimate and displays `period information unavailable`.

While the table is open, it checks only the local date every 60 seconds and checks again on focus and tab return. If a service date or the UTC date of a rejection record changes, it displays a status notice and performs no automatic API query. A wrong device clock does not change the server query period. The periodic timer stops while hidden, and close, page or connection change, and unmount release the timer and event listeners.
