# Tallyfin 프론트엔드 설계

이 문서는 화면 구조와 상태 처리 계획이며, 프로토타입 코드나 UI 코드가 아니다. 프레임워크는 아직 확정하지 않는다(UNDECIDED).

2026-10-08에 프로젝트 개요 시안을 선택했다. 화면 구현은 [선택한 디자인 기준](./SELECTED_VISUAL.md)과 저장한 원본 이미지를 따른다.

## 화면 구성

프로젝트 목록에서 프로젝트를 고른 뒤 개요·이벤트 분석·목표/작업 흐름·설정을 메뉴로 탐색한다. 각 화면은 서버의 프로젝트 권한 검사 결과를 전제로 렌더링한다.

1. 프로젝트 목록: 접근 가능한 프로젝트를 나열하고 새 프로젝트로 진입한다.
2. 프로젝트 개요: 등록 이벤트의 요약 지표와 최근 추이를 보여준다.
3. 이벤트 분석: 이벤트별 건수·추이·허용 속성별 집계를 조회한다.
4. 목표/작업 흐름: 등록된 시작·성공·실패의 건수와 완료율을 본다. 새로고침/기기 간 연결과 고급 퍼널은 후속 설계다.
5. 프로젝트 설정: 이벤트·속성의 자료형/허용 값/한도, 스키마 버전, 발행 출처와 권한을 관리한다. 등록·수정 권한을 조회 권한과 구분한다.

프로젝트를 전환하면 이전 프로젝트의 캐시를 비우고 진행 중인 요청을 취소해, 다른 프로젝트 데이터가 섞이지 않게 한다. 늦게 도착한 이전 응답이 화면을 덮어쓰지 않도록 취소 토큰을 함께 사용한다.

## 데이터 표시

비율 옆에는 해당 분자·분모 건수를 함께 보여준다. 단순 이벤트 건수에는 임의의 비율을 붙이지 않는다. 기간·시간대·정의 버전·집계 대상·발행 출처를 확인할 수 있게 하고, 서로 다른 완료 정의를 한 비율로 합치지 않는다. 차트와 표는 같은 데이터와 기준을 사용한다. Sembom의 tool/mode 같은 필드는 프로젝트별 선택 속성으로 다룬다.

## 권한과 데이터 경계

프로젝트 권한은 서버에서 강제하며, 클라이언트는 그 결과만 반영한다. 권한이 없는 프로젝트는 목록에 노출하지 않거나, 진입 시 unauthorized 상태로 처리한다.

## 상태 처리

empty, unknown, loading, error, stale, unauthorized 상태를 각각 구분해 표시한다. 분모가 없어 계산할 수 없는 값은 0이 아니라 unknown으로 표현하고, 0으로 위장하지 않는다. 데이터가 오래된 경우 stale로 알린다.

## 접근성

키보드만으로 주요 탐색과 조회가 가능해야 하고, 320px 너비에서도 레이아웃이 무너지지 않아야 한다.

## MVP와 이후

MVP의 전환 화면은 같은 메모리 작업 흐름의 완료율을 보여준다. 임의 다단계 퍼널·고유/재방문 사용자 분석·서버/기기 간 연결은 초기 메뉴에 노출하지 않는다. 샘플 프로토타입은 아래에 구현했고, 실제 서버 연결과 운영 프레임워크 선택은 후속 작업으로 둔다.

## 샘플 프로토타입 — 2026-10-08

[prototypes/admin](../../prototypes/admin/README.md)의 단일 화면에서 네 메뉴를 전환한다.
App은 프로젝트·기간·메뉴·샘플 상태·프로젝트별 표시 이름을 메모리에 소유한다.
Dashboard는 개요·이벤트 검색/정렬/선택·목표와 차트/수치 표를 렌더링하며,
Settings는 이름 입력과 검증을 소유한다. data.ts는 고정 날짜의 샘플과 집계만 제공한다.
서버 상태와 URL 상태는 아직 없으며 새로고침 시 초기화한다.

React·Recharts·Phosphor·Inter·Noto Sans KR는 이 프로토타입에서만 사용한다.
API/DB 계약과 운영 기술 선택을 확정하지 않는다. 실제 권한은 서버 연결 시 강제한다.
검증 증거와 남은 차이는 [디자인 QA](../../prototypes/admin/design-qa.md)를 참고한다.

참고: 제품 스펙은 [02-spec.md](../product/02-spec.md)를 따른다.

## 관리자 API·로그인 연결 — 2026-10-08

`LiveDashboard`는 같은 출처 `/v1`의 서버 상태와 프로젝트·조회 조건을 소유하고,
연결 해제나 샘플 모드 전환 시 데이터와 진행 중 요청을 비운다. `OidcLogin`은 API
연결 모드에서 지연 로드되며 로그인 진행·설정 없음·오류 상태를 표시한다. bearer
직접 연결은 접힌 보조 입력으로 제공한다.

`/auth/callback`은 첫 렌더링 전에 인가 응답을 URL에서 제거하고 API 모드로 진입한다.
`BrowserLogin`은 PKCE 거래와 메모리 토큰을 소유하며 연결 성공 후 API 클라이언트가
세션 정리를 맡는다. 취소된 로그인은 토큰을 화면에 연결하지 않는다. React StrictMode의
effect 재실행은 같은 코드 교환을 공유한다. 권한은 서버의 프로젝트 grant로 강제한다.

로그인 설정·보관·갱신의 조건은 [OIDC 문서](../backend/oidc.md#브라우저-관리자-로그인)를
따른다. 실제 제공자와 운영 로그인 배포는 미정이다.

## 수집 상태 진단 — 2026-10-10

API 연결 모드의 설정 상단 `CollectionDiagnostics`가 읽기 전용 진단을 소유한다.
`loadCollectionDiagnostics`는 설정과 선택 스키마를 병렬 조회하고 스키마를 읽었을
때만 프로젝트-local 오늘의 요약을 조회한다. `generatedAt`과 마지막 신규 수신 시각을
프로젝트 시간대로 보여준다. 마지막 수신은 선택 날짜/버전과 무관한 프로젝트 전체
기록이며 중복 재전송으로 갱신되지 않는다. 오늘의 건수는 선택 버전의 browser 이벤트
집계로 UTC 수신일 할당량 사용량과 다르다. 별도 요청의 결과는 원자 스냅샷으로 간주하지 않는다.

프로젝트 상태·선택 스키마 상태·설정 한도를 표시한다. 각 조회 실패는 별도로 표시하고
읽을 수 있는 다른 값은 유지한다. 요약 실패나 스키마 미확인은 수신 기록 없음/0으로
채우지 않는다. null 수신 기록만 기록 없음으로 표시하며 장애 여부를 추측하지 않는다.
메타의 프로젝트·버전·날짜·시간대와 등록 browser 이벤트·중복·합계·안전 정수 및
UTC 시각 형식을 검사한다. `generatedAt`은 DB 조회 전에 정해지므로 동시에 들어온
수신 시각이 이보다 늦을 수 있다. 프로젝트/클라이언트/버전/새로고침 키와 취소로
이전 응답을 버리고 언마운트 때 요청을 정리한다.

마운트·버전 변경·설정 저장·스키마 선택/발행·명시적 새로고침 때만 읽고 자동 폴링이나
시험 이벤트는 보내지 않는다. 서비스 주소는 Local UI State로 탭 안에서 `URL.origin`을
허용 목록과 정확히 비교한다. 주소·토큰을 전송/저장하거나 URL State에 기록하지 않는다.
reader에게 설정 변경을 제안하는 대신 소유자에게 요청하도록 안내한다. 로딩/부분 실패/
기록 없음/읽기 전용과 재시도 상태, 입력 라벨/설명·상태 안내를 제공하며 모바일은 한 열이다.
`CollectionRejections`를 연결해 최근 7개 UTC 날짜의 프로젝트 전체 거부 요청 건수와
마지막 거부 시각을 보여준다. 고정 10종 원인별 표와 최근 날짜부터의 일별 표는 접힌
details로 제공한다. 표 글자는 1rem이며 작은 화면에서는 표 영역만 가로로 스크롤한다.
거부 조회는 스키마와 무관하게 설정·스키마와 병렬로 실행하고 다른 조회의 성공/실패와
독립적으로 표시한다. UTC 수신일 기준은 프로젝트 시간대의 오늘 이벤트와 구분한다.
원인별·일별 합계, 모든 날짜, 원인 중복과 UTC 시각을 검증하며 누락·손상 응답을 0으로
채우지 않는다. 저장은 best-effort이고 도입 전 이력을 채우지 않아 기록이 누락될 수
있음을 안내한다. 거부율·현재 한도 사용량은 API도 제공하지 않는다.
접힌 확인 순서는 실제 실패 이력과 구분하고 SDK 정의·출처·429/Retry-After·
오류 코드/requestId를 확인하도록 안내한다. API·DB·SDK·의존성·운영 인증 경계는 그대로다.

## 프로젝트 설정 편집 — 2026-10-09

`LiveSettings`는 `ApiClient`와 프로젝트 ID, `refreshTick`, 선택적 `registry`를 받고
`SettingsEditor` 컨트롤러가 소유한 상태만 렌더링한다. 컨트롤러는 스냅샷·초안과
phase(loading/ready/saving/review/error)·필드 오류·잠금을 소유하며, 컴포넌트는 effect에서
컨트롤러를 만들고 구독한 뒤 정리한다. `refreshTick`이 바뀌면 `refresh()`를 호출하고
첫 마운트에서는 중복 요청을 피한다. `onSaved`는 저장 성공 시 프로젝트 표시 이름을
갱신하도록 부모에 알린다.

폼은 이름(1~80자), 상태(수집 중/일시정지), 허용 출처(textarea, 한 줄 1개 최대 16개),
분당 요청(1~600), UTC 하루 신규 수신(1~1000000)을 편집한다. 프로젝트 ID·시간대는 서버
값이라 읽기만 보여준다. 저장 중에는 입력과 저장 버튼을 비활성화하고 진행 상태를
알린다. 오류는 필드별 `aria-invalid`·오류 문구로 표시하고 첫 오류 필드로 포커스를
옮긴다.

서버가 준 `canEdit`가 false이거나 owner 권한이 없어 403이면 입력을 그대로 두고 편집을
잠근다. 충돌 409나 응답 유실(네트워크/503 등)에서는 저장을 잠그고 입력을 보존한다.
`최신 설정 확인`으로 최신 서버 값을 읽어 비교 표로 보여준 뒤 `서버 설정 사용`과
`내 변경 유지하고 검토`를 명시적으로 고른다. 하단에는 `registry`가 있으면 등록
이벤트·작업 흐름 표를 읽기 전용으로 보여주고, 없으면 스키마 조회가 필요하다는 설명만
둔다. 설정 조회는 집계 기간·스키마 조회와 분리했고, 바뀐 항목만 PATCH로 보낸다.
`onSaved`는 최신 서버 설정을 채택할 때도 프로젝트 표시 이름을 갱신한다. 동시 변경을
검토할 때 내가 편집하지 않은 항목은 최신 서버 값을 유지한다. 검증 결과는
[검증 기록](../../VALIDATION.md)에 정리한다.

## 스키마 편집 상태·API 연결 — 2026-10-09

`SchemaEditor`는 프로젝트별 버전 목록·권한 snapshot, JSON 초안·발행 번호·검증 결과·
개인정보 검토 확인과 loading/ready/validating/publishing/review/error 상태를 메모리에
소유한다. 변경 후에는 검증·검토 확인을 초기화하며 자동 발행 재시도는 하지 않는다.
409·403·응답 유실 시 초안을 보존하고 최신 서버 정의를 조회해 명시적으로 선택한다.
응답 유실 뒤에는 대상 버전을 읽고 제출한 canonical 정의와 일치할 때만 발행을 확인한다.
프로젝트 전환·연결 해제·언마운트는 요청을 취소하고 늦은 응답을 무시한다.
`ApiClient`는 목록 GET·초안 검증 POST·발행 PUT 응답을 검사하며 발행 hash도 제출한
정의와 비교한다. 서버 API·DB 계약은 바꾸지 않는다.

`LiveSchemas`는 API 연결 모드의 설정 화면 아래에 독립된 섹션으로 연결한다. 현재
조회 기간·분석용 선택 버전과 별개로 버전 목록·최신 정의를 읽고, 목록은 최신순·이전
버전 더 보기로 표시한다. 버전 불러오기는 JSON 초안을 명시적으로 교체하는 동작이다.
새 버전 번호·JSON textarea·이벤트 미리보기·정의 검증·개인정보 검토 확인·발행을
제공한다. 서버 검증 오류의 pointer·고정 문구를 표시하고 textarea로 포커스를 옮긴다.
발행은 현재 초안·버전의 검증과 검토 확인이 모두 있을 때만 가능하다. 폼·버전 목록·
오류·비교 영역은 labels/caption/scope와 키보드 스크롤을 제공하며 reader 정의는
복사할 수 있는 readOnly textarea로 표시한다. 409·응답 유실 복구에서 서버/내 정의를
나란히 보여주고 명시적인 사용/유지 선택을 요구한다. 모바일에서는 비교를 세로로
배치하고 표·JSON 내용은 내부 스크롤을 사용한다. 초안은 브라우저에 저장하지 않는다.

## 프로젝트 생성 상태 — 2026-10-09

ApiClient의 명시적 POST /v1/projects는 16KiB 상한과 응답 ID·원본 요청 hash를 검사한다.
ProjectCreator는 입력·필드 오류·생성 중·불확실·생성 확인·설정 조회 상태를 소유한다.
입력은 브라우저 메모리에만 두며 생성 권한을 프로젝트 owner에서 추론하지 않는다.
409/403은 입력을 보존해 수정·권한 확인을 허용하고, 응답 유실·잘못된 성공 응답은
원본 요청을 잠근다. 명시적인 같은 요청 확인만 POST를 다시 보내며 자동 재전송하지 않는다.
확인 뒤 설정 GET 실패는 생성 결과를 유지하고 조회만 재시도한다. 연결 종료·언마운트는
요청을 취소하며 늦은 응답으로 프로젝트를 열지 않는다. 입력 한도는 기본 값을 미리
채우되 빈 값은 기본값으로 대체하지 않는다. 화면 연결은 아래에 정리한다.

## 프로젝트 생성 화면·SDK 연결 안내 — 2026-10-09

API 연결 툴바의 `프로젝트 추가`가 `LiveProjectCreate`를 열고, `ProjectCreator`가 입력·
필드 오류·생성 중·불확실·생성 확인·설정 조회 상태를 소유한다. 폼은 이름·공개 ID·IANA
시간대·허용 출처를 받고 `수집 한도`를 접어 분당 요청·UTC 하루 신규 수신을 입력받는다.
단계 표시(1 프로젝트 · 2 이벤트 스키마 · 3 SDK 연결)로 순서를 안내한다.

생성 권한은 서버가 확인하며 프로젝트 owner로 추론하지 않는다. 403은 입력을 보존한 채
운영자에게 생성 권한을 확인하라고 알린다. 409는 입력을 보존한다. ID 충돌은 ID 필드에
오류를 표시하고 포커스를 옮기며, 생성 개수 한도는 한도 안내만 보여준다. 응답 유실
(네트워크/503 등)에서는 입력을 잠그고 같은 요청으로 생성 여부를 확인하는 동작만
제공하며 자동 재전송하지 않는다. 확인 뒤 설정 조회가
실패하면 생성 결과를 유지하고 조회만 다시 시도한다. 연결 종료·언마운트는 요청을
취소하고 늦은 응답으로 프로젝트를 열지 않는다.

생성 성공은 프로젝트를 목록에 넣고 그 프로젝트를 선택한 뒤 설정 화면으로 이동한다.
설정 화면 위에 프로젝트 완료·이벤트 스키마·SDK 연결 단계를 표시하고 스키마 등록으로
안내한다.

설정 화면 아래 `LiveSdkSetup`은 최신 발행 스키마만 읽어 연결 코드를 만든다. 투영에는
browser 출처 이벤트와 작업 흐름만 넣고 서버 출처 이벤트·bearer·서버 전용 정의는 넣지
않는다. 수집 서버 출처는 관리자 화면 주소와 같다고 가정하지 않고 직접 입력받아 HTTPS
또는 로컬 개발 주소만 허용한다. SDK는 아직 공개 패키지가 아니라 저장소에서
`npm run build:browser`로 로컬 빌드한 `packages/browser`를 연결하도록 안내한다. 코드
복사 실패는 직접 선택하도록 안내한다. 새 스키마 버전을 발행하면 버전 입력과 안내가
최신 번호로 갱신된다. 스키마 검증이 browser 출처 이벤트를 하나 이상 요구하므로 서버
출처 이벤트가 섞인 정의에서도 연결 코드가 만들어지고, 그 코드에서 서버 출처 이벤트는
제외된다.

## 스키마 이벤트 폼 — 2026-10-09

`LiveSchemas`의 스키마 섹션에 `SchemaEventForm` 컴포넌트를 추가했다. 폼은 초안의
이벤트를 목록으로 보여주고 추가·삭제와 name(최대 48자)·label(최대 80자)·출처
(browser/server) 입력을 제공한다. 새 이벤트는 browser 출처와 빈 `properties {}`로
만들며 최대 50개까지 허용한다. 속성과 작업 흐름은 뒤에 정리한 각각의 폼에서
편집한다.

폼과 JSON은 `SchemaEditor.state.draft` 한 원본을 쓴다. 폼 변경도
`editor.edit('draft', ...)`로 보내므로 검증 결과·개인정보 검토 확인 초기화와
phase(validating/publishing/review/more) 잠금 규칙을 JSON 편집과 똑같이 따른다.
폼은 이벤트의 name·label·source만 바꾸고 각 이벤트의 properties와 workflows, 그 밖의
추가 키는 그대로 보존한다. JSON은 접힌 `JSON 직접 편집`에서 기존처럼 원문을
수정한다.

초안이 파싱되지 않거나 폼으로 표현할 수 없는 JSON(배열이 아닌 events/workflows,
객체가 아닌 이벤트나 지원하지 않는 출처 등)이면 폼 수정을 막고 `JSON 직접 편집`으로 안내하며
초안은 그대로 보존한다. 작업 흐름의 startEvent·successEvent·failureEvent에 연결된
이벤트는 name·출처·삭제를 잠그고 label만 편집하게 한다.

검증 오류 초점은 이벤트 관련 오류를 해당 폼 필드로 옮기고, 그 밖의 오류는 JSON 영역을
펼쳐 그 위치로 초점을 옮긴다. 이벤트를 추가·삭제하면 새 항목이나 다음 항목으로 초점을
옮긴다. 이벤트가 없을 때 폼은 첫 이벤트를 추가하라는 짧은 설명만 보여준다. reader는
폼을 읽기 전용으로 열고 검증·발행·검토·더 보기 잠금은 그대로 유지한다. 기존 시안
스타일을 그대로 쓰며 새 시안은 만들지 않는다. API·DB·의존성·CI·위생·운영 계약은 바꾸지
않는다.

## 스키마 속성 폼 — 2026-10-09

`SchemaEventForm`의 각 이벤트 아래에 접히는 `SchemaPropertyForm`을 추가했다. 접힌 요약은
`N번 이벤트 속성 편집 · 등록 개수 / 4`처럼 등록한 속성 수를 보여주고, 그 이벤트의 속성에
걸린 검증 오류가 있으면 속성 폼을 자동으로 펼쳐 해당 필드로 초점을 옮긴다. `LiveSchemas`는
속성 오류 대상(`propertyIssueTarget`)을 먼저 찾고, 없으면 기존 이벤트 오류 대상을 쓰고,
둘 다 없으면 JSON 영역을 펼친다.

폼은 속성 추가·삭제와 이름(최대 48자)·자료형(boolean/enum/integer)·필수 여부·수집
목적(최대 240자)·enum 허용 값(한 줄에 하나)·정수 최솟값·최댓값을 편집한다. 속성 이름은
영문 소문자로 시작하는 48자 이내이고 이벤트마다 최대 4개까지 등록한다. 새 속성은 아직
쓰지 않은 `property_N` 이름과 boolean·필수 아님·빈 수집 목적으로 만든다.

자료형을 바꾸면 이전 자료형의 전용 필드(`values`·`minimum`·`maximum`)를 대체하고 enum은
빈 목록, integer는 최솟값 0·최댓값 1에서 시작한다. 수집 목적·필수 여부와 그 밖의 추가
키는 그대로 두고 다른 키를 자동으로 고치지 않는다. 이미 다른 속성이 쓰는 이름으로
바꾸면 기존 정의를 덮어쓰지 않고 거부한다.

정수 입력은 정수로 읽히고 안전 정수 범위에 있으면 숫자로, 빈 값·불완전한 값·범위 밖
문자열은 문자열 그대로 초안에 남긴다. 0으로 대체하지 않으므로 서버 검증을 통과하기
전에는 발행할 수 없다. enum 허용 값의 빈 줄·중복도 자동으로 지우지 않는다. 허용 값은
소문자나 숫자로 시작하는 32자 이내 값만 유효하다.

가능한 조합 수는 폼에서 미리 계산해 `가능한 조합 N개 / 256`으로 보여준다(속성별 허용 값
32종, 이벤트 조합 256개 이하). 입력이 덜 차서 계산할 수 없으면 완성하라는 안내를,
256개를 넘으면 줄이라는 오류를 표시한다. 이 숫자는 편집 피드백이고 최종 판정은 서버
검증이 한다. 수집 목적에는 원시 입력값·개인 정보 대신 용도와 허용 범주만 적으라는
안내를 둔다.

작업 흐름의 `dimensions`에 쓰이는 속성은 이름·자료형·필수 여부·허용 값·범위·삭제를
잠그고 수집 목적만 편집한다. 그 밖의 속성은 작업 흐름에 연결된 이벤트에서도 그대로
편집한다. 변경은 같은 `editor.edit('draft', ...)`로 보내므로 한 원본 초안을 공유하고
검증 결과·개인정보 검토 확인 초기화와 phase 잠금 규칙이 JSON 편집과 같다. 속성 정의를
폼으로 표현할 수 없거나 초안이 파싱되지 않으면 폼 수정을 막고 원문을 보존한 채
`JSON 직접 편집`으로 안내한다.

각 속성은 fieldset·label로 묶고 설명·오류를 `aria-describedby`로 연결하며 오류 필드에
`aria-invalid`를 표시한다. 추가·삭제 버튼에는 이벤트·속성 번호를 담은 `aria-label`을
둔다. 속성을 추가하면 새 속성 이름으로, 삭제하면 다음 항목 이름으로 초점을 옮긴다.
reader는 이 폼도 읽기 전용으로 열린다. 작업 흐름은 아래 작업 흐름 폼에서 편집한다.
API·DB·의존성·CI·위생·운영 계약은 바꾸지 않고 검증 수치는
[검증 기록](../../VALIDATION.md)에 둔다.

## 스키마 작업 흐름 폼 — 2026-10-09

`LiveSchemas`의 스키마 섹션에서 이벤트 폼 아래, 접힌 `JSON 직접 편집` 위에
`SchemaWorkflowForm`을 추가했다. 폼은 초안의 작업 흐름을 목록으로 보여주고 추가·삭제와
ID(최대 48자)·표시 이름(최대 80자)·시작·성공·실패 이벤트·비교 기준 속성 입력을
제공한다. 작업 흐름은 최대 10개까지 등록한다. 새 흐름은 아직 쓰지 않은 `workflow_N` ID와
browser 출처, 빈 시작·성공 문자열, `null` 실패, 빈 비교 기준으로 만든다.

정의는 그대로 불변이며 폼 편집은 발행 대상 초안만 바꾼다. 폼과 JSON은
`SchemaEditor.state.draft` 한 원본을 쓰고 폼 변경도 `editor.edit('draft', ...)`로 보내므로
검증 결과·개인정보 검토 확인 초기화와 phase(validating/publishing/review/more) 잠금
규칙을 JSON 편집과 똑같이 따른다.

이벤트 선택은 browser 출처 이벤트만 보여준다. 등록되지 않았거나 비어 있는 선택 문자열도
`(사용할 수 없음)` 옵션과 빈 값 자리 표시자로 목록에 남겨 그대로 보존한다. 실패 이벤트의
`null`은 `실패 단계 없음`으로, 빈 문자열은 별도 자리 표시자로 구분하며, `null`은 유효한
이벤트 이름이 될 수 없는 예약 sentinel로 select 값에 매핑한다. ID·표시 이름·비교 기준
아래에는 각각 영문 소문자 48자·1~80자·단계마다 같은 자료형의 필수 속성이라는 입력 안내를
둔다.

비교 기준 체크박스는 단계 이벤트들의 필수 속성과 이미 선택된 항목의 합집합으로 보여준다.
최대 4개까지 고르며, 4개가 차면 이미 선택한 항목만 다시 눌러 해제할 수 있도록 새 항목
체크박스만 비활성화한다. 단계별 자료형·허용 값이 어긋난 선택도 목록에서 지우지 않고 그대로
보여준다.

폼은 단계 중복과 비교 기준 자료형·허용 값 불일치를 실시간 경고로 보여준다. 이 경고는
편집 피드백이고 최종 판정은 서버 검증이 한다. ID 중복은 로컬에서 거부하고 문제가 된 ID
입력으로 초점을 옮긴다. 초안이 파싱되지 않거나 폼으로 표현할 수 없는 JSON(배열이 아닌
workflows, 객체가 아닌 흐름, browser가 아닌 출처, 문자열이 아닌 단계, 배열이 아닌 비교
기준)이면 폼 수정을 막고 `JSON 직접 편집`으로 안내하며 초안은 그대로 보존한다. 추가·삭제
뒤에는 새 항목이나 다음 항목(없으면 추가 버튼)으로 초점을 옮긴다.

각 흐름은 fieldset·legend로 묶고 레이블·설명·경고·오류를 `aria-describedby`로 연결하며
검증 오류 필드에 `aria-invalid`를 표시한다. 검증 오류 초점은 작업 흐름 관련 오류를 해당
폼 필드로 옮기고, 그 밖의 오류는 기존처럼 속성·이벤트 폼이나 JSON 영역을 쓴다. reader는
이 폼도 읽기 전용으로 열리고 검증·발행·검토·더 보기 잠금은 그대로 유지한다. 폼은 기존
시안 스타일을 그대로 쓰고 좁은 화면에서는 입력 열을 한 줄로 접어 가로 스크롤을 만들지
않는다. API·DB·의존성·CI·위생·운영 계약은 바꾸지 않는다.

## 이벤트 속성 분석 — 2026-10-09

API 연결 모드의 이벤트 분석 화면은 browser 출처 이벤트를 고르면 그 이벤트에 등록된
속성 중 하나를 분류 기준으로 선택하게 한다. 선택은 프로젝트·스키마 버전·이벤트 조합
(context)에 묶어 두고, 프로젝트·스키마 버전·이벤트가 바뀌거나 그 속성이 정의에서
사라지면 이전 선택을 버리고 다시 고르게 한다. 조회는 기존 같은 출처 관리자 API의
`GET /v1/projects/{id}/events/{name}/daily`를 `groupBy`와 함께 호출하며, 프로젝트나
조회 조건이 바뀌면 진행 중 요청을 취소하고 늦게 도착한 응답이 다른 데이터를 덮지
않게 한다.

`analyzeEventSeries`가 일별 응답 전체를 먼저 검사한다. 등록 정의와 어긋난 값·날짜·합계가
있으면 차트나 비중을 만들지 않고 멈추고, 통과한 경우에만 전체 합계와 값별 건수·비중·
일별 건수를 담은 `PropertyAnalysis`를 만든다. `EventPropertyBreakdown`은 부모가 검증한
이 값만 받아 렌더링하며 여기서 예외를 던지지 않는다.

속성 값 표는 값·건수·비중을 `caption`·`scope`와 합계 행으로 보여주고, 값 버튼
(`aria-pressed`)으로 한 값을 고르면 표와 아래 `Trend`가 같은 선택을 써서 그 값의 일별
건수를 그리고 값이 바뀌면 둘 다 함께 갱신된다. 32개
곡선을 한 번에 그리지 않고 표는 모든 값을, 차트는 선택한 값 하나만 보여준다. 비중은
‘값별 건수 ÷ 선택한 이벤트 전체 건수 × 100’이고 전환율이 아니다. 표시 비중은 소수점 한
자리로 반올림해 값별 합이 100.0%와 조금 다를 수 있다. 분모가 0이라
계산할 수 없으면 0이 아니라 `—`로 두고 합계 값을 지어내지 않는다. true·false·null은
각각 `참 (true)`·`거짓 (false)`·`값 없음`으로 구분하며, null은 필수 아님 속성의 별도
값으로 따로 센다. 표는 키보드 스크롤과 내부
가로 스크롤을 두고 좁은 화면에서도 무너지지 않게 최소 너비를 풀어 둔다. API·DB·의존성·
CI·위생·운영 계약은 바꾸지 않는다.

## 작업 흐름 속성별 완료율 — 2026-10-10

API 연결 모드의 목표에서 각 흐름 아래 `WorkflowPropertyBreakdown`을 둔다. 등록된
workflow.dimensions 중 한 속성을 직접 고르고 기본은 분류 안 함이다. 시작 시점의
속성 값별 시작·성공·실패·대기·완료율을 표로 보고 값 버튼으로 일별 내역을 연다.
값은 관찰된 것만 표시하며 false·0의 자료형을 유지한다. 성공/시작으로 완료율을
계산하고 시작0이면 —, 실패 단계가 없으면 실패 수 —다. 집계 중 코호트를 안내한다.
현재 기간만 분류하고 속성별 직전 기간 비교는 후속이다.

같은 출처의 새 workflow breakdown API를 선택 때만 조회한다. `validateWorkflowBreakdown`은
메타·등록 분류·값의 자료형/범위·중복·일별 날짜/합계·완료율·버킷 합계를 검사한다.
전체 목표와 속성 응답의 생성 시각은 다를 수 있으므로 두 응답을 임의로 맞추지 않는다.
부모는 현재 조회 키에 묶인 상태만 CSV에 반영하고 조건 변경·분류 해제·언마운트는
요청을 취소하며 늦은 응답을 버린다. 속성 오류는 전체 목표를 유지하고 별도 재시도를
제공한다. 속성 조회가 미완료/오류면 CSV를 잠그고 분류 해제나 복구를 안내한다.
CSV의 workflow_property_summary/total/day 행은 현재 기간의 선택 분류와 모든 관찰
값/일별 수치를 보존하며 빈 결과에서도 summary 행에 분류를 남긴다.

## CSV 내보내기 — 2026-10-10

API 연결 모드의 개요·이벤트 분석·목표에서 `CSV 내려받기`를 제공한다.
`CsvDownload`는 현재 조회 키에 묶인 검증 결과를 받아 클릭할 때만 `analyticsCsv`로
CSV와 Blob을 만들고 임시 다운로드 링크를 사용한다. 추가 서버 요청이나 영구 저장은
없고 링크와 object URL을 정리한다. 현재 집계, 선택한 상세, 활성 비교가 준비되지
않았거나 실패하면 버튼을 잠그고 조회 완료·상세 닫기·비교 해제를 안내한다.
조건이 바뀌면 다운로드 피드백도 초기화한다. CSV에 토큰·엔드포인트·원문 이벤트는 넣지 않는다.

CSV는 고정 열을 가진 긴 형태다. 프로젝트·스키마·시간대·기간·생성 시각·검색어·선택
이벤트·분류 기준을 각 행에 기록한다. `record_type`으로 전체/이벤트/흐름 합계, 일별 수치,
속성 값별 합계/일별, 비교 지표를 구분하고 `period`는 current/previous/comparison이다.
개요는 등록 이벤트와 대표 흐름, 목표는 모든 흐름, 이벤트 분석은 검색한 이벤트와 선택
상세를 포함한다. 활성 비교 표의 범위는 검색과 무관하므로 CSV 비교 행도 같은 범위를 쓴다.
속성은 관찰된 모든 값과 그 값의 일별 수치를 넣고 선택된 그래프 값 하나로 제한하지 않는다.
null/boolean/number/string을 `value_type`으로 구분한다. 건수·비율·변화량은 표시용 반올림
이전 수치를 쓰고 percent와 percentage_point를 구분한다. 값 없음은 빈 칸이며 서버 이벤트는
unsupported, 계산 불가 비교는 not_available로 표시한다. 조회 시각이 다른 결과는 generated_at이
다를 수 있다. UTF-8 BOM·CRLF·큰따옴표 이스케이프를 사용하고 수식 시작 문자/제어문자로
시작하는 텍스트에는 작은따옴표를 추가한다. 숫자의 음수에는 추가하지 않는다.
[OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection)을 참고했으며,
스프레드시트에서 다시 저장·열기까지 보편적인 방어를 보장하지 않는다. API·DB 계약은 그대로다.

## 직전 기간 비교 — 2026-10-10

API 연결 모드의 개요·이벤트 분석·목표에서 `직전 기간과 비교`를 직접 켠다.
최근 7·14·30일(오늘 포함)을 프로젝트 시간대 기준으로 바로 앞 같은 일수와 비교한다.
두 구간은 동일한 스키마 버전으로 기존 summary·workflow daily API를 각각 조회해
31일 조회 한도를 지킨다. 기본은 꺼짐이며 추가 조회는 켰을 때만 발생한다.
`loadPeriod`는 현재·이전 응답의 프로젝트·시간대·버전·날짜·등록 이벤트·일별 합계를
검사한다. `PeriodComparison`은 검증한 스냅샷만 받고 개요의 대표 흐름, 이벤트별 건수,
목표의 각 흐름 시작·성공·완료율을 표로 보여준다. 건수는 증감률(%), 완료율은 차이(%p)다.
이전 건수가 0이면 증감률을 계산하지 않고, 완료율이 null이면 비교 불가로 표시한다.
오늘은 집계 중이며 provisional 시작일 코호트는 완료율이 바뀔 수 있다고 안내한다.
비교의 loading·error·retry 상태는 현재 결과와 분리한다. 조건·모드 변경과 비교 해제 시
요청을 취소하고 조회 키가 다른 응답은 숨긴다. 표에는 caption·scope와 내부 가로 스크롤을
둔다. API·DB·SDK·의존성·운영 계약은 바꾸지 않는다.
