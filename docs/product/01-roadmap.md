## Remaining Work — 2026-10-21

The current core analytics functionality has been implemented locally. Use the list below as the basis for the next work; do not treat past “next steps” left in dated records as a list of unimplemented work.

1. Finalize the actual administrator/publisher OIDC provider, client, audience, operational accounts, D1, and domain, and connect them with the existing installation tool. The authentication code and installation tool are implemented; actual values and operational connections remain.
2. Apply the remote Worker, D1 migration, Cron, and service bindings, then verify actual login, collection, cleanup, and backup/recovery. Distinguish local load/recovery results from remote results.
3. Connect the operational path for repeatedly running authentication-access checks, consecutive-failure/recovery criteria, and alert recipients. `monitor:access` uses explicit policy and state files to make local decisions about consecutive failures, recoveries, and alert intent. Manual access checks, log summaries, and a local report screen also exist. The actual schedule, recipients, SLO, owners, and retention period are undecided. [Access Monitor](../../tools/runtime/ACCESS-MONITOR.md).
4. Activate the actual Sembom integration and verify aggregation, missing events, service latency, and mobile cost. Then verify generality in one service of a different type. Repository examples differ from an actual installation.
5. Decide additional bot-blocking and temporary IP handling policies. Per-project per-minute and daily limits are currently implemented.
6. Prepare the public SDK packages and distribution procedure under the adopted Apache-2.0 license and [contribution terms](../../CONTRIBUTING.md#license). The browser and server packages remain `private: true` at `0.0.0`; public scope, release method, and npm publication remain separate work. `verify:sdk-packages` performs an offline check of installation, type information, and ESM entry points in a separate project from local tarballs. [Package Verification](../../tools/sdk/README.md).

File save and load for schema drafts has been implemented locally. A `tallyfin.schema-draft/v1` file stores the current JSON and the version to publish; loading clears previous validation and personal-data review so they must be checked again. Files are read only in the browser, and there is no automatic validation or publication. Explicit save/read and revision-conflict recovery for a project-specific owner-shared server draft have also been implemented locally. Version reservation is follow-up scope. Comparison of event, property, workflow, and funnel definitions between two published versions has been implemented and verified locally in settings. Aggregation and conversion-rate comparison across different versions, linking existing workflows across refreshes or devices, and other storage adapters are also follow-up work, and are not conditions that must all be added before the pilot. Evidence for implementation status is in the [product specification](02-spec.md), [risk register](03-risk-register.md), and [validation record](../../VALIDATION.md). Actual configuration choices, pushes, deployments, and publication are separate work.
